ASSESSMENT STRICTNESS & UX IMPROVEMENTS - JANUARY 5, 2025
============================================================

OVERVIEW
--------
Changes made to improve assessment modules' scoring accuracy, prevent exploits 
with empty/short recordings, and fix UX issues related to tab-switching.


PROBLEM STATEMENT
-----------------
1. Empty/short recordings getting high scores: Users could submit empty or very 
   short recordings (less than 3 seconds) and receive artificially high scores.

2. Tab-switch resets assessment: When using dev tools to skip to a specific 
   module (e.g., Conversation), switching tabs would reset back to Pronunciation.

3. Recording duration too long: 120-second max was excessive for conversation prompts.

  MIN_DURATION_SECONDS = 3    (was 10, minimum to submit)
  MIN_RECOMMENDED_DURATION = 10   (was 20, tip for best scoring)

Behavior:
  - Submit button is disabled if recording is less than 3 seconds
  - User sees red error text if less than 3 seconds: "Recording too short"
  - User sees amber tip if 3-10 seconds: "For better results, try 10+ seconds"
  - Auto-stops at 60 seconds


File: src/pages/Assessment.tsx

Tab-switch reset fix:
When using dev tools to skip to a specific module via sessionStorage, the phase 
is now persisted to the database immediately after the session loads.

Code added after loading session:
  if (devPhase) {
    await supabase
      .from("assessment_sessions")
      .update({ current_module: devPhase, current_item_index: 0 })
      .eq("id", sessionData.id);
  }

Effect: Tab switches no longer reset the user's module position.

RATIONALE
---------

Why 3 seconds/words instead of 5?
  The speaking prompts in speaking.json are open-ended questions that users might 
  answer quickly if they speak fast. Examples:
    - "Parlez d'un objectif important pour vous cette annee."
    - "Racontez un moment recent ou vous etiez fier/fiere de vous."
  
  A fluent speaker could give a valid short response in 3-5 seconds. The threshold 
  of 3 prevents abuse (empty submissions) while allowing natural variation.

Why 60 seconds max?
  60 seconds is sufficient for a thoughtful response. 120 seconds was excessive 
  and could lead to user fatigue.

Why persist dev phase to database?
  The dev phase override was only stored in sessionStorage, which is cleared on 
  re-render. By saving to the database, the module position persists across tab 
  switches, page refreshes, and browser restarts.
